# Deploying to Hostinger — launch-day runbook

Follow this top to bottom. Steps are ordered so that a failure stops you before
it can do damage: nothing writes to the database until the environment is
proven, and nothing goes public until the smoke test passes.

**Read [`launch-security-checklist.md`](launch-security-checklist.md) first.**
This runbook assumes it has been worked through.

Throughout: `~/domains/rehletsehha.com` is the account root and
`~/domains/rehletsehha.com/app` is where the project goes. **The project does
not go in `public_html`.** Step 3 explains why.

---

- [ ] `./vendor/bin/pint --test` — passes

- [ ] `npm run build`
- [ ] Note the built filenames from `public/build/manifest.json`. You are

- [ ] Password generated by hPanel, not reused from anywhere.

- [ ] Confirm `app/public/build/manifest.json` exists. Without it every page

## 3. Document root — the step that matters most

- [ ] hPanel → Websites → Domain → **document root = `app/public`**.

**What breaks if this is wrong.** Point the domain at `app/` and the entire
project becomes web-reachable. `https://rehletsehha.com/.env` then returns your
database password, mail password and `APP_KEY` as plain text — and `APP_KEY` is
what decrypts every patient's medical history. `storage/logs/laravel.log` is
served too.

This is not hypothetical: it is exactly the exposure the pre-launch audit
found, and it is the single highest-severity mistake available on launch day.

**Verify before going further:**

```bash
curl -sI https://rehletsehha.com/.env          # expect 404
curl -sI https://rehletsehha.com/storage/logs/laravel.log   # expect 404
curl -s  https://rehletsehha.com/ | head -5    # expect HTML
```

A `200` on either of the first two means **stop and fix the document root.**

- [ ] Belt and braces: `app/.htaccess` (shipped in this repo) denies dotfiles
      and `storage/` even if the root is wrong. It is a second line, not a
      substitute for the first.

## 4. PHP version and extensions

- [ ] hPanel → Advanced → PHP Configuration → **PHP 8.2 or newer**.

The code targets `^8.2` and has been developed on 8.5. No 8.3-or-later syntax
is used, but it has never been executed below 8.5 — see
[what-must-be-verified-on-the-host](#c--what-only-the-host-can-confirm).

Required extensions: `gd` (with WebP), `intl`, `mbstring`, `pdo_mysql`,
`openssl`, `curl`, `fileinfo`, `zip`, `bcmath`, `exif`.

## 5. `.env`

- [ ] `cp .env.example .env` on the server.
- [ ] Fill in `DB_*`, `MAIL_PASSWORD`, `APP_URL`.
- [ ] Leave `ADMIN_PASSWORD` and `DOCTOR_PASSWORD` **empty** — the seeder then

## 6. `APP_KEY` — once, and never again

- [ ] `php artisan key:generate --force`

**This runs exactly once, before the first migration, and never again.**

- It must **not** equal the local key. Generating fresh on the server is what
  guarantees that; do not copy a key between environments.
- It must **never** be regenerated after data exists. Every intake form is
  encrypted with it; a new key orphans every medical record irrecoverably.
- `key:generate` appears in **no** automated path — not in composer scripts,
  not in any deploy script. That is deliberate and must stay true.
- Back the key up somewhere that is not the server, now.

See [`APP_KEY.md`](APP_KEY.md) for the recovery procedure if it is ever lost.


- [ ] `--no-dev` — Debugbar, Pest and PHPStan must not reach production.

## 8. Migrate and seed

```bash
php artisan migrate --force
php artisan db:seed --force
```

One `db:seed`, not a hand-written list. `DatabaseSeeder` already has the right
order — `WorkingHoursSeeder` after `DoctorUserSeeder`, because it attaches
hours per practitioner and silently skips itself if no doctor exists — and
enumerating seeders by hand is how `AppKeyFingerprintSeeder` and
`ServiceSpecialtySeeder` get forgotten.

It is safe to run in production:

| Seeder | On production |
|---|---|
| `DemoAppointmentSeeder` | **Guards itself** — refuses outside `local`. Invented patients with invented phone numbers never reach the live database. |
| `TestimonialSeeder` | Deliberately empty. The three invented testimonials were removed; real reviews arrive only through a patient's own invitation. |
| `PostSeeder` | Seeds three articles as **drafts**. They are placeholder clinical prose with no named reviewer, and the model refuses to publish them. Harmless, and the article index correctly shows its empty state. |

- [ ] **Write down the admin and doctor passwords.** They are printed once and
      never again; `ADMIN_PASSWORD`/`DOCTOR_PASSWORD` were left empty in step 5
      precisely so the seeder generates strong ones.
- [ ] `php artisan clinic:verify-key` — on a fresh database this **records**
      production's fingerprint rather than comparing. That is the intended
      first run.

## 9. Storage symlink

```bash
php artisan storage:link
ls -la public/storage        # expect a symlink to ../storage/app/public
```

Video thumbnails are fetched once and served from `/storage/…`. Without the
link they 404 and the gallery falls back to placeholders.

**If the host blocks symlinks** (some shared plans do, and some wipe them on
redeploy):

1. Try `ln -s ../storage/app/public public/storage` directly.
2. If that fails, make `public/storage` a real directory and add a nightly
   `cp -ru storage/app/public/. public/storage/` to cron. Ugly but reliable.
3. Re-check after **every** deploy — a wiped symlink is silent.

## 10. Caches — in this order

```bash
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan filament:assets
```

Order matters: `config:cache` first, because the others read configuration
while building. If you edit `.env` afterwards you **must** re-run
`config:cache` — a cached config ignores `.env` entirely, and this is the
classic "why is it still using the old password" hour.

Never run `config:cache` while `APP_DEBUG=true`.

## 11. Cron

One line. hPanel → Advanced → Cron Jobs:

```
* * * * * cd ~/domains/rehletsehha.com/app && php artisan schedule:run >> /dev/null 2>&1
```

This single entry drives everything:

| Task | Cadence | What it does |
|---|---|---|
| `queue:work --stop-when-empty --max-time=50` | every minute | Drains queued mail. **There is no long-running worker on shared hosting** — this is the substitute. |
| `clinic:send-reminders` | every minute | 24-hour and 1-hour reminders |
| `clinic:verify-key` | 03:00 | Fingerprint check |
| `model:prune` | 03:30 | Log retention |
| `clinic:send-daily-schedule` | 07:00 Cairo | The clinic's day |
| `clinic:send-review-requests` | 10:00 Cairo | Review invitations |

- [ ] `php artisan schedule:list` shows all six.

### If Hostinger enforces a 5-minute minimum

Some plans do. The consequences, precisely:

- **Confirmation emails arrive up to 5 minutes late.** The booking itself is
  instant; only the mail waits. Acceptable.
- **`--max-time=50` is now wrong.** With a 5-minute gap the worker should run
  longer: change it to `--max-time=280` in `routes/console.php` so it drains
  continuously rather than idling for four and a half minutes.
- **Reminders are unaffected in accuracy.** This is worth being precise about,
  because it is the thing most likely to be got wrong:

  The sweep is **window-based**, not exact-minute. A reminder fires when
  `starts_at` is within the lead window and the row is unsent. So a coarser
  cron *delays* the send by up to one interval — it never misses it.

  **The 24-hour reminder's copy says «بكرة» (tomorrow), and that stays true
  under a 5-minute lag**: the window opens at `starts_at − 24h` and the message
  goes out within five minutes of that, so the appointment really is ~23h55m
  away.

  **It stops being true if cron stops.** If the scheduler is down for six
  hours, a patient three hours from her appointment is told it is tomorrow.
  That is a cron-outage failure, not a cadence one — monitor step 13.

## 12. Post-deploy verification

```bash
php artisan about                       # environment=production, debug=off
php artisan clinic:verify-key           # records the fingerprint on first run
php artisan clinic:verify-copy --strict # must exit 0
php artisan schedule:list
```

- [ ] `curl -sI https://rehletsehha.com/.env` → **404**
- [ ] `curl -sI https://rehletsehha.com/admin` → 302, with `X-Robots-Tag: noindex`
- [ ] Sign in to `/admin` as the administrator and **complete two-factor
      enrolment**. The panel forces it for the `admin` role
      (`isRequired: fn () => auth()->user()?->hasRole('admin')`), so the
      enrolment screen should appear before the dashboard does. Confirm it
      actually does — a forced enrolment that silently does not fire is the
      same as no second factor.

      The secret lives in `users.app_authentication_secret`, and recovery codes

      somewhere off the server.** Losing both the authenticator and the codes
      locks the only administrator out of the panel.

Then run [the first-hour smoke test](#d--first-hour-smoke-test).

## 13. Monitoring, from day one

- [ ] **`https://rehletsehha.com/up`** — the one URL worth bookmarking. It
      answers **200** when the site is well and **503** when it is not, and it
      checks the six things that fail *silently*: the database, disk space, the
      cache, the scheduler, the message queue, and the age of the last backup.
      None of those are visible to a visitor; the site keeps serving pages
      perfectly through every one of them.

      Point an uptime monitor at it — UptimeRobot's free tier is enough — and
      set the alert on the **status code**, not on the page text. Add
      `?format=json` for a machine-readable answer.

      The page itself is written for whoever is at the front desk: each line
      says what has stopped working *for a patient* rather than which
      subsystem is down. It is deliberately unauthenticated, and equally
      deliberately says nothing but names and pass/fail — no versions, no
      paths, no error text.

- [ ] `storage/logs/laravel.log` — check daily for the first week.
- [ ] Admin → the delivery log. Any row stuck at `queued` for more than a few
      minutes means **cron is not running**. This is the single most useful
      signal on the whole site: it catches a dead scheduler before a patient
      notices a missing reminder. `/up` now catches the same thing
      automatically, but the log tells you *which* messages were lost.
- [ ] Any `failed` row with a reason. A `skipped` row is normal — it means a
      patient gave no email address.

## 14. Backups

### What is backed up, and what is not

**The database, nightly, and nothing else.**

The code is in git and the served photography with it; the original downloads
are documented in `docs/media/photography.md` and can be fetched again. What
cannot be recreated from anywhere is the appointments, the patients and the
intake forms.

Archiving the whole application directory every night would take minutes on
shared hosting, eat the disk quota, and produce files nobody would ever
restore from. A dump of this practice's database is a few hundred kilobytes.

Two commands run through the **same cron entry as everything else** (step 11 —
there is no second schedule to forget):

| Time (Cairo) | Command | What it does |
| --- | --- | --- |
| 02:00 | `backup:clean` | Applies the retention policy |
| 02:30 | `backup:run --only-db` | Writes the night's dump |

Both before `clinic:verify-key` at 03:00, so a morning that starts with a key
mismatch already has last night's dump sitting beside it.

### Where they go

```
~/domains/rehletsehha.com/app/storage/app/private/Rehlet Sehha/YYYY-MM-DD-HH-MM-SS.zip
```

Outside the document root, and `storage/app/private/.gitignore` ignores
everything in it, so an archive cannot be committed by accident.

### How long they are kept

Seven days of every dump, then thinned: sixteen daily, eight weekly, four
monthly. Seven days covers the ordinary case — somebody deletes the wrong
record on Friday and nobody notices until Monday. The months cover the slower
one: a data problem introduced weeks ago and only visible now.

Hard cap of **500 MB**, far above what that policy can actually use. It exists
to bound the failure that hurts: a full disk stops new intake forms saving.

### Encrypt them, and write the password down

- [ ] Set `BACKUP_ARCHIVE_PASSWORD` in `.env` **before the first dump is
      written**, and store it in the same place as `APP_KEY` — off this server.
      See [APP_KEY.md](APP_KEY.md).

On the server the dump and the `.env` sit on the same disk, so this buys
nothing against somebody already inside the account. What it protects is the
copy that *leaves*, and copies do leave — see the monthly download below. That
file lands in a downloads folder, gets attached to an email, ends up on a
laptop. Encrypted it is a nuisance; unencrypted it is the practice's entire
patient list.

> **An archive encrypted with a password nobody recorded is not a backup.** It
> is a zip file that will never open again, and you find that out on the day
> you need it. Never rotate the password: every older archive becomes
> unopenable the moment you do.

### Who is told when one fails

`BACKUP_ALERT_EMAIL` in `.env`. Set it to **a person who will act**, not to the
address on the contact page.

Only failures are ever sent. There is deliberately no nightly "backup
succeeded" email: it would be filtered into a folder within a fortnight, and
once it is filtered the *failure* email — same sender, same shape of subject —
is filtered with it. `/up` is what confirms the good nights.

### Off the server, once a month

- [ ] Download the newest archive to a machine that is not this server.

A backup that only exists on the machine it backs up is not a backup. It does
not survive a deleted account, a billing lapse, or a hosting migration that
goes wrong — and those are more likely than disk failure.

```bash
scp -P 65002 'USER@HOST:~/domains/rehletsehha.com/app/storage/app/private/Rehlet Sehha/*.zip' ~/rehlet-backups/
```

Delete the local copies you no longer need. They are patient records.

## Restoring from a backup

Read this **before** you need it. Every step assumes you have already stopped
the site with `php artisan down --render=errors::503`.

### 1. Unpack the archive

```bash
php artisan clinic:unpack-backup
```

With no arguments it picks the newest archive and unpacks it to
`storage/app/private/restore`. Pass a path to choose a different one.

> **Do not use `unzip`.** When `BACKUP_ARCHIVE_PASSWORD` is set the archive is
> AES-256, and Info-ZIP `unzip` — which is the `unzip` on Hostinger, on macOS,
> and on most Linux boxes — **cannot read AES zips**. It does not fail in a way
> that looks like failure either; it prints
>
> ```
> skipping: db-dumps/….sql  need PK compat. v5.1 (can do v4.5)
> ```
>
> and exits leaving an empty directory. On the day you need a restore, that
> line is indistinguishable from a corrupt backup, and the reasonable
> conclusion — "our backups are broken" — is wrong. `clinic:unpack-backup` goes
> through PHP's `ZipArchive`, which reads them correctly and is by definition
> installed.

### 2. Import the dump

Deliberately manual. A command that overwrites a live database on one keystroke
is a command that will one day be run against the wrong one.

```bash
mysql -u USER -p DATABASE < storage/app/private/restore/db-dumps/mysql-DATABASE.sql
```

### 3. Check the key before you believe anything

```bash
php artisan clinic:verify-key
```

**A restored database is unreadable without the `APP_KEY` that encrypted it.**
The intake forms are encrypted at the application layer, so a dump restored
onto a server with a different key is a table of unreadable strings — and
nothing will tell you until somebody opens a patient record. If this command
reports a mismatch, stop and find the right key. Do not "fix" it by
regenerating one. See [APP_KEY.md](APP_KEY.md).

### 4. Confirm the data is actually there

```bash
php artisan tinker --execute='
  echo App\Models\Appointment::count()." appointments\n";
  echo App\Models\IntakeForm::query()->whereNotNull("conditions")->first()?->conditions."\n";
'
```

The second line is the one that matters: it reads through the decryption. If it
prints Arabic, the restore is genuinely complete. If it throws a
`DecryptException`, the key is wrong and step 3 lied to you about which
database it was checking.

### 5. Clean up, then come back up

```bash
rm -rf storage/app/private/restore   # every patient record, in plain text
php artisan up
```

### Practise it once, on the test database

A restore procedure nobody has run is a document, not a capability. Do it once
on `rehlet_sehha_test` before you need it on a Tuesday morning.

## Rollback

Assume a release goes wrong at step 10 or later.

**If the schema did not change** (no new migration in the release):

```bash
cd ~/domains/rehletsehha.com
rm -rf app && mv app-previous app
cd app
php artisan config:cache && php artisan route:cache && php artisan view:cache
```

So: **before every deploy, `cp -a app app-previous`.** That is the rollback.

**If a migration ran**, code rollback alone is not enough and may be worse than
the fault:

1. `php artisan down --render=errors::503`
2. Restore the database from the pre-deploy dump (step 1 of every deploy:
   `mysqldump -u USER -p DB > ~/backups/pre-deploy-$(date +%F-%H%M).sql`).
3. Restore the code as above.
4. `php artisan up`

**Never** roll back by running `migrate:rollback` against production data
without reading the migration's `down()` first. Several of ours drop columns.

**Never** regenerate `APP_KEY` as part of a rollback. It will not fix anything
and it destroys every encrypted intake form.

## C — What only the host can confirm

Every one of these is an assumption the local machine cannot settle. Run them
over SSH **before** step 8, because each one changes what you do next.

| # | Assumption | Command | Expected | If not |
|---|---|---|---|---|
| 1 | **PHP ≥ 8.2** | `php -v` | `8.2` or newer | Raise it in hPanel → PHP Configuration. Composer will refuse to install otherwise. |
| 2 | **The CLI and the web use the same PHP** | `php -v` then a `phpinfo()` page | Same minor version | Hostinger can run different versions for CLI and FPM. Cron uses the CLI one; a mismatch means the site and the scheduler disagree about what is installed. |
| 3 | **GD with WebP** | `php -r 'var_dump(function_exists("imagewebp"));'` | `bool(true)` | Only needed to *regenerate* photography (`clinic:process-photos`). The served WebP set is committed, so the site works without it — but you cannot add a photograph until it is enabled. |
| 4 | **intl** | `php -r 'var_dump(extension_loaded("intl"));'` | `bool(true)` | Arabic date formatting degrades to English month names. |
| 5 | **Symlinks permitted** | `php artisan storage:link && ls -la public/storage` | A symlink | Use the copy-based workaround in step 9. Video thumbnails 404 until then. |
| 6 | **MySQL or MariaDB, and which version** | `php artisan tinker --execute='echo DB::selectOne("select version() v")->v;'` | MySQL ≥ 5.7.8 or MariaDB ≥ 10.2 | **Nothing in this schema cares.** JSON columns are used for translations, but never with JSON path operators — spatie/translatable reads whole columns into PHP. No generated columns, no fulltext indexes. Developed against MySQL 8.0.46; MariaDB is fine. |
| 7 | **Cron actually runs, and how often** | Add the entry, wait 5 minutes, then `php artisan schedule:list` and watch `storage/logs` | Tasks firing | If it is 5-minutely, change `--max-time=50` to `--max-time=280`. See step 11. |
| 8 | **Outbound SMTP from the host** | `php artisan tinker --execute='Mail::raw("host smtp check", fn($m) => $m->to("you@example.com")->subject("check"));'` then drain the queue | Mail arrives | Some shared hosts block outbound 465/587 to external servers. Hostinger's own SMTP over `localhost` is the fallback. **Nothing else in this runbook matters if this fails** — a clinic that cannot email confirmations is not live. |
| 9 | **The queue drains** | `php artisan queue:work --stop-when-empty` by hand | Jobs process | If jobs stick, check `failed_jobs` and the delivery log. |
| 10 | **Disk headroom** | `du -sh ~/domains/rehletsehha.com` and hPanel's quota | Comfortable margin | `storage/logs` grows; `LOG_LEVEL=warning` keeps it slow. |
| 11 | **HTTPS with a valid certificate** | `curl -sI https://rehletsehha.com` | `200`, no TLS warning | The clipboard copy button needs a secure context. Without it, patients with no email fall back to manual copy on the one screen holding their booking reference. |
| 12 | **Timezone of the CLI** | `php -r 'echo date_default_timezone_get();'` | Anything — the app pins UTC internally | Only matters if it disagrees wildly; scheduled times are computed by Laravel, not the shell. |
| 13 | **`mysqldump` exists and is reachable** | `php artisan backup:run --only-db` | `Backup completed!` and a zip under `storage/app/private/` | The single assumption the whole backup story rests on, and one the local machine cannot settle. Some shared hosts do not ship the MySQL client binaries at all. If it is missing, set `'dump_binary_path'` in `config/database.php` to wherever it lives, and if it genuinely is not installed, say so — **do not go live believing there are backups.** |
| 14 | **The archive can be reopened on the server** | `php artisan clinic:unpack-backup --to=/tmp/restore-drill && ls /tmp/restore-drill/db-dumps && rm -rf /tmp/restore-drill` | A `.sql` file | Proves the password in `.env` actually opens the archive the server just wrote. Do this on **launch day**, not on the day of an incident. |
| 15 | **`/up` answers honestly** | `curl -s https://rehletsehha.com/up?format=json` | `"status":"ok"` with all six checks `true` | Expect `scheduler` to be `false` until cron has run once, and `backup` to be `false` until the first dump. Both going green is how you know steps 11 and 14 really worked. |

## D — First-hour smoke test

Run in order. **A failure at any step stops the rest** — each depends on the
one before, and continuing past a failure only makes the diagnosis harder.

### 1. The site answers

```bash
curl -sI https://rehletsehha.com/ar        # 200
curl -sI https://rehletsehha.com/.env      # 404  ← if this is 200, take the site down
curl -s  https://rehletsehha.com/up?format=json
```

The third one is the only check here that looks *behind* the page. Expect:

```json
{"status":"ok","checks":{"database":true,"storage":true,"cache":true,"scheduler":true,"queue":true,"backup":true}}
```

`scheduler` stays `false` until cron has run once, and `backup` until the first
nightly dump — so on launch morning those two may legitimately be red. Come
back to this after step 6.

*Stop if:* anything but 200/404, or `database` is `false`.

### 2. Book a real appointment

In a browser, as a patient would: pick a service, a slot, fill in your own
name and **a real email address you can read**, tick consent, confirm.

- [ ] The confirmation screen shows a reference like `RS-XXXXXXXX`.

*Stop if:* the wizard errors, or no reference appears. Check
`storage/logs/laravel.log`.

### 3. The confirmation email arrives

- [ ] Wait up to 1 minute (or 5, on a coarse cron). Check the inbox.
- [ ] Check spam as well — and if it is there, that is a DNS problem, not a
      code one. See [`mail-authentication.md`](mail-authentication.md).
- [ ] Admin → delivery log shows `sent`, not `queued` or `failed`.

*Stop if:* the row says `queued` after five minutes — **cron is not running**.
Fix that before anything else; every reminder depends on it.

*Stop if:* the row says `failed` — read the reason. `View not found` means an
incomplete deploy; an SMTP error means item 8 of section C was never true.

### 4. The manage link works

- [ ] Open the link in the email.
- [ ] The page shows the booking, and offers reschedule and cancel.
- [ ] Reschedule to another slot. Confirm the email arrives.
- [ ] Cancel. Confirm the email arrives.

*Stop if:* the link 404s — the token route or `APP_URL` is wrong.

### 5. The admin panel

- [ ] `/admin` loads and redirects to the login.
- [ ] Sign in as the administrator; complete two-factor enrolment.
- [ ] The appointments list shows the booking you just made.
- [ ] Open it. The medical information section is present.
- [ ] Working hours screen lists the week.

*Stop if:* the panel renders unstyled — `filament:assets` did not run, or
`public/build` was not uploaded.

### 6. The queue drains on its own

- [ ] `php artisan tinker --execute='echo DB::table("jobs")->count();'` → `0`
      within a minute or two of any action that sends mail.

*Stop if:* it climbs. The scheduler is not running the worker.

### 7. Only then, tell anyone the site is live

- [ ] Delete the test appointment (admin → cancel, then delete).
